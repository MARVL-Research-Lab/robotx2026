    The ground station

    One program holds the mission. It drives three vehicles over MAVLink, speaks the RoboCommand protocol to the judges, and keeps enough state that an interruption costs seconds rather than a run.

    Architecture

    Vehicles talk MAVLink. The ground station talks MQTT and protocol buffers to RoboCommand. Between the two sits one orchestrator that owns every piece of mission state, and everything else reads from it: the terminal console, the three dimensional course view, and the protocol client.

    The adapter interface is the reason this works. A simulated vehicle, a firmware build running software in the loop and a real hull all implement the same adapter, so the mission code above them has never had to know which one it is driving.

    Three state machines

    State lives in three places, each with one job.

    What each machine owns.
    MachineOne perStates
    VehiclevehicleOFFLINE, BOOTING, READY, AUTONOMOUS, TASK_EXECUTING, RETURNING, EMERGENCY_STOP
    Tasktask attemptINACTIVE, QUEUED, ASSIGNED, IN_PROGRESS, COMPLETE, FAILED, ABORTED
    MissionrunIDLE, PRE_RUN_CHECK, RUNNING, EMERGENCY, COMPLETE

    Each task also carries an ordered list of steps, which is what the console shows as a previous, current and next triple. A step is the smallest thing the mission can be resumed at.

    Interrupt and resume

    Task 4 is the reason the design looks like this. RoboCommand can interrupt a run at any moment with an assistance request, a keep-out zone or a moving vessel. The vehicle in the affected domain has to acknowledge on the wire, break off whatever it was doing, respond, and then carry on.

    When an incident arrives the orchestrator writes a checkpoint: the task, the step it reached, the progress through the step list and the score events already earned. The vehicle then runs the incident as its own task. When the incident clears, the checkpoint is restored and the vehicle picks up at the step it stopped on rather than at the start of the task.

    Keep-out zone, Advanced tier30 sSimulated

    A keep-out zone arrives mid transit. The console acknowledges it, the boat routes around the area, and the safe passage attempt resumes afterwards.

    Health and escalation

    A heartbeat monitor watches every vehicle. Missed heartbeats and low battery raise alerts, and sustained heartbeat loss escalates to an emergency stop rather than waiting for an operator who may be looking at the water rather than the screen. Battery thresholds are per vehicle, because a quadrotor at 20 percent is a different problem from a boat at 20 percent.

    Before any run the console can run a pre-run gate: every vehicle reachable and in a ready state, every battery above its minimum, and all three domains present. It is non-destructive and can be run mid-mission.

    The operator console

    The console is a terminal application, which is a deliberate choice: it runs over a shell connection from a laptop in a marquee on the promontory, it does not need a browser, and it redraws fine over a slow link. The layout is fixed so that an operator can find the same number in the same place under pressure.

    The RoboCommand link

    Handbook 3.4 defines how teams report to the judges: MQTT over TCP on port 1883, protocol buffer payloads from RoboNation's schema release, four topics, and a run start handshake that gates the whole run. Our client implements it, and we have run it against RoboNation's own test server.

    The four topics, from handbook 3.4.7.
    PurposeTopicDirection
    Course configurationrobocommand/robotx/courseTo us, retained
    Vehicle reportrobocommand/robotx/SUTD/<vehicle>/reportFrom us
    Team requestrobocommand/robotx/SUTD/requestFrom us
    Team commandrobocommand/robotx/SUTD/commandTo us

    Reports go out at 2 Hz per vehicle carrying state, position, speed, heading, roll, pitch, altitude or depth, current task and vehicle type, with flight phase added for the aircraft. Sequence numbers are per vehicle for reports and per team for requests, and a response quotes the sequence number of the message it answers.

    The run start sequence and the log it produced are on the proof of readiness page, step by step.

    Design decisions

    Three machines rather than one

    A vehicle can be autonomous while its task is suspended and the mission is in an emergency. Collapsing those into one machine would need a state for every combination.

    Checkpoints outside the task machine

    A checkpoint has to survive the task machine being reset, because that is what an interruption does to it. Keeping it separate is what makes resume a data restore rather than a replay.

    Depth hold counts as autonomous

    Only for the underwater vehicle, which cannot hold a position it does not know. The rest of the fleet has to be in a real guided mode to count.

    Only the consumed streams are requested

    ArduPilot's default stream set would saturate a HaLow link. The adapter asks for position at 4 Hz and status at 1 Hz, and re-asks if telemetry stops.

    The ground station carries 154 automated tests covering the state machines, the orchestrator lifecycle, suspend and resume, the protocol end to end, the embedded broker, the course layout and the readiness rehearsal. See the test record.
